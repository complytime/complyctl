## Context

See proposal.md for motivation. The current `complyctl.spec` (v0.0.8)
uses manual `go build`, disables debuginfo, and lacks go-vendor-tools
integration. The decisions reversed here (manual `go build`, disabled
debuginfo, `%goprep -k` vendor preservation) were appropriate at the
time of `specs/005-rpm-packaging-ci` but are now superseded by
go-vendor-tools adoption and alignment with current Fedora guidelines.

Fedora 43 ships Go 1.25 while `go.mod` requires Go 1.26.5. The Packit
config uses `propose_downstream` to sync releases to dist-git.

Key upstream constraints:
- `cmd/` contains four binaries; only `cmd/complyctl` ships in the RPM
- `vendor/` is committed upstream for development builds
- The man page at `docs/man/complyctl.1` is pre-generated via `make man`
- PR #5 on src.fedoraproject.org proposed go-vendor-tools adoption for
  v0.0.10 but was never merged and is now outdated

## Goals / Non-Goals

**Goals:**
- Debuginfo packages produced correctly on all Fedora targets
- Vendored dependency licenses machine-verified via go-vendor-tools
- Spec file aligned with current Fedora Go packaging guidelines
- Copr PR builds and `propose_downstream` both generate vendor archives
- Local developer testing possible before submitting changes
- Fedora 43 builds work despite Go version mismatch

**Non-Goals:**
- Switching Packit from `propose_downstream` to `pull_from_upstream`
- Packaging additional binaries (`behavioral-report`, `test-provider`,
  `mock-oci-registry`)
- Generating the man page during RPM build (it is pre-built upstream)
- Removing vendor/ from the upstream git repository
- Changes to the upstream Go source code or build system

## Decisions

### D1: Use `%gobuild` macro instead of manual `go build`

**Choice**: Replace the manual `go build -buildmode=pie ...` with the
`%gobuild` macro, passing custom version ldflags via `GO_LDFLAGS`
environment variable.

**Rationale**: `%gobuild` automatically adds build-id generation
(`-B 0x...`), external linkmode, DWARF preservation
(`-compressdwarf=false`), and hardened linker flags. This is what makes
debuginfo work. Manual invocation missed all of these.

**Alternative considered**: Keeping manual `go build` with the required
flags added explicitly. Rejected because it duplicates logic already
maintained in `go-rpm-macros` and would drift over time.

### D2: Use `%gometa -f` without `-L` flag

**Choice**: `%gometa -f` (not `-L -f` as PR #5 used).

**Rationale**: The `-L` flag enables versioned package naming for Go
modules with major version path suffixes (e.g., `/v2`). Testing
confirmed identical output with and without `-L` for
`github.com/complytime/complyctl`. The flag adds no value and increases
cognitive load.

### D3: Separate vendor archive via go-vendor-tools (Source1)

**Choice**: Source0 is the upstream tarball. Source1 is a vendor archive
generated by `go_vendor_archive create`. Source2 is `go-vendor-tools.toml`.

**Rationale**: This is the standard Fedora Go packaging approach. It
enables machine-verified license scanning of all vendored code and
supports security patching of individual vendored dependencies via
`dependency_overrides` in the toml config.

The `%prep` section uses `%goprep -A` (autosetup mode) which runs
`%autosetup` instead of `%setup` and removes the upstream `vendor/`
directory (default behavior without `-k`). Then `%setup -q -T -D -a1`
unpacks the Source1 vendor archive on top, replacing the upstream
`vendor/` with the go-vendor-tools-generated version. The `-A` flag
is the standard approach when using go-vendor-tools with separate
Source1 vendor archives.

**Alternative considered**: Using vendor/ from the upstream tarball
(`%goprep -k`). Rejected because it bypasses license verification and
cannot apply dependency overrides.

### D4: `%gocheck2` for unit tests with exclusions

**Choice**: Use `%gocheck2` from go-vendor-tools with `-t` flags to
exclude test directories and non-shipping cmd packages.

Exclusions:
- `-t %{goipath}/tests` (E2E, integration, acceptance, cross-repo,
  behavioral, and schema-validation test trees)
- `-t %{goipath}/cmd/test-provider` (test tooling, not shipped)
- `-t %{goipath}/cmd/mock-oci-registry` (test tooling, not shipped)
- `-t %{goipath}/cmd/behavioral-report` (assessment tool, not shipped)

Note: `%gocheck2` compiles all packages in the module tree but only
runs tests for non-excluded packages. The `-t` flag excludes packages
recursively from testing. All Go packages under the excluded paths
either: (a) have build tags that prevent compilation (E2E tests use
`//go:build e2e`), or (b) are standalone commands with no reverse
imports from the main `complyctl` binary. The vendor archive produced
by `go_vendor_archive create` includes all transitive dependencies
needed to compile the full module tree.

**Rationale**: `%gocheck2` is `GO111MODULE`-aware and reads import paths
from `go.mod`, which matches our vendor-based module build. The older
`%gotest` requires `GO111MODULE=off` by default. Excluding non-unit test
directories avoids failures from missing external dependencies (OCI
registries, providers, network access).

### D5: Packit `post-modifications` action for both contexts

**Choice**: A single `post-modifications` action that detects whether
it is running in release-syncing context (`$PACKIT_DOWNSTREAM_REPO` set)
or SRPM-creation context, and generates the vendor archive accordingly.

The concrete shell logic (passed via `bash -c` to satisfy Packit's
command tokenization):
```sh
set -xeuo pipefail
export GOTOOLCHAIN=local
if [ -n "${PACKIT_DOWNSTREAM_REPO:-}" ]; then
  cd "$PACKIT_DOWNSTREAM_REPO"
fi
go_vendor_archive create --config go-vendor-tools.toml complyctl.spec
go_vendor_license \
  --config go-vendor-tools.toml \
  --path complyctl.spec \
  report --verify-spec --autofill=auto
```

Context detection:
- **SRPM creation (Copr builds)**: `$PACKIT_DOWNSTREAM_REPO` is not set.
  The action runs in the upstream repo working directory where Source0
  tarball already exists (created by Packit's `create-archive` step).
  `srpm_build_deps` ensures `go-vendor-tools` and `golang` are
  installed. The generated vendor archive is included in the SRPM.
- **Release syncing (propose_downstream)**: `$PACKIT_DOWNSTREAM_REPO`
  is set. The action `cd`s to the downstream repo where Source0 has
  been downloaded. The generated vendor archive and any files not
  tracked in dist-git are automatically uploaded to the Fedora
  lookaside cache by Packit before the PR is created.
- **Error handling**: Both `go_vendor_archive create` and
  `go_vendor_license report` are run under `sh -xeuc` (exit on error).
  If either command fails, the action exits non-zero, which causes
  the Packit job to fail with the error output visible in logs.

**Rationale**: The `post-modifications` action runs at the right point
in both workflows: after spec modifications and before SRPM build or
lookaside upload. Using `srpm_build_deps` ensures `go-vendor-tools` and
`golang` are available in the Copr SRPM build environment.

**Alternative considered**: Separate actions per job type. Rejected
because Packit replaces the entire `actions` mapping per job (no merge),
leading to duplication.

### D6: `go-vendor-tools.toml` lives in the upstream repo

**Choice**: Maintain `go-vendor-tools.toml` in the upstream repo and
sync it to dist-git via `files_to_sync`.

**Rationale**: Enables local testing (`go_vendor_archive create`
and `go_vendor_license report` can run against the local spec). The file
is small and changes infrequently. Keeping it upstream ensures a single
source of truth and avoids manual dist-git maintenance.

### D7: Keep Fedora 43 Go version compatibility hack

**Choice**: Retain the conditional sed block that patches `go.mod` and
`vendor/modules.txt` for Fedora 43 (Go 1.25). The condition uses
`%if 0%{?fedora} == 43`.

**Rationale**: Fedora does not bump major Go versions within a release.
F43 will remain on Go 1.25.x until EOL (2026-12-09). The `go.mod`
requires Go 1.26.5. Removing the hack would break F43 builds.

Note on sed patterns:
- `go.mod` sed: `s/^go [0-9].*/go 1.25/` -- matches **any** Go version
  directive (resilient to both patch and minor version bumps)
- `vendor/modules.txt` sed: should be generalized to match any version
  greater than 1.25 (not just `1.26.*`) to handle transitive dependency
  version bumps during the remaining F43 lifecycle. Recommended pattern:
  `sed -i '/^## explicit; go /s/go [0-9]\..*/go 1.25/' vendor/modules.txt`

### D8: `%autorelease` for Release tag

**Choice**: Replace `Release: 1%{?dist}` with `Release: %autorelease`.

**Rationale**: Modern Fedora convention. Automatically increments on
rebuilds and is already used by Packit-managed packages.

### D9: Remove CentOS Stream targets temporarily

**Choice**: Remove `centos-stream-9-x86_64` and `centos-stream-10-x86_64`
from `.packit.yaml` `copr_build` and `tests` target lists. Add a YAML
comment noting that CentOS Stream support requires `go-vendor-tools`
availability on those platforms.

**Rationale**: `go-vendor-tools` is a Fedora-specific package not
available in CentOS Stream repos or EPEL. Supporting both platforms
would require conditional macros (`%if 0%{?fedora}` guards around 6+
spec sections, different `%prep` and `%files` logic), essentially
maintaining two build paths in one spec file. This complexity is not
justified while `go-vendor-tools` remains Fedora-only. CentOS Stream
targets can be restored when the tooling becomes available there.

**Alternative considered**: Conditional `%if 0%{?fedora}` guards in the
spec with fallback to upstream vendor/ on CentOS. Rejected due to
complexity (different `%prep`, `%install`, `%files` paths) and
maintenance burden of two divergent build paths.

## Risks / Trade-offs

- **[Risk] `go_vendor_license` fails to detect some vendored licenses**
  -> Mitigation: The `go-vendor-tools.toml` supports manual license
  entries (`[[licensing.licenses]]`) with sha256 pinning. Run
  `go_vendor_license report --prompt --autofill=auto` during initial
  setup to populate overrides.

- **[Risk] Copr SRPM build environment lacks network for module proxy**
  -> Mitigation: Copr builders have network access. The
  `go_vendor_archive create` command downloads modules via the Google
  Go module proxy by default. If needed, `use_module_proxy = false` can
  be set in the toml.

- **[Risk] F43 sed hack becomes stale if go.mod toolchain version
  changes** -> Mitigation: The `go.mod` sed uses `s/^go [0-9].*/go 1.25/`
  which matches any Go version directive, making it resilient to both
  patch and minor version bumps. The `vendor/modules.txt` sed should be
  generalized to match beyond `1.26.*` (see D7). The `%if` conditional
  ensures it only applies on F43.

- **[Trade-off] `go-vendor-tools.toml` license overrides are
  version-specific** -> When vendored dependencies change significantly,
  the toml may need updates. The `--verify-spec` flag in the Packit
  action will fail loudly if the license expression changes, prompting
  maintainer review.

- **[Risk] Go module integrity in vendor archive** -> Mitigation: Go
  module downloads are verified against `sum.golang.org` via `go.sum`
  checksums. The vendor archive inherits this verification chain.

## Maintenance Workflow

When vendored dependencies change (e.g., after `go mod tidy` and
`make vendor`), the `go-vendor-tools.toml` license overrides may need
updating. The workflow:

1. Regenerate the vendor archive locally:
   `go_vendor_archive create --config go-vendor-tools.toml complyctl.spec`
2. Re-run license detection:
   `go_vendor_license --config go-vendor-tools.toml --path complyctl.spec
   report --prompt --autofill=auto`
3. If the SPDX expression changed, update the `License:` tag in the spec
4. Commit the updated `go-vendor-tools.toml` and spec

If a Packit build fails with a license mismatch (`--verify-spec` error),
the developer runs steps 1-4 above to synchronize the toml with the
current vendored dependencies.
